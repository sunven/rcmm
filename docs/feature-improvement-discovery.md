# rcmm 功能完善与优化建议

日期：2026-10-08

## 评估范围与结论

按 brainstorm-ideas-existing 技能，从产品、设计、工程三个视角各提出 5 个想法，再综合选出前 5 项。

默认目标：完善核心功能与使用体验，让用户从配置到 Finder 实际执行更可靠、更可理解。目标用户按 DESIGN.md 定位：经常在 Finder 中打开项目目录、运行命令、创建文件的 Mac 用户，尤其是开发者和重度效率工具用户。

本次基于当前仓库源码、README、DESIGN.md 静态阅读；没有运行应用、复现故障或获取真实用户数据。因此，代码行为是依据，发生频率、影响程度和需求强度仍需验证。工作量仅作相对估计，尚不是排期承诺。

**建议先完善“首次验证、编辑保存、执行反馈、多选语义、组合失败策略”，再扩展功能种类。** 这些更贴合“可靠系统工具”的既定定位。

## 已有能力，不应重复建设

- Finder 菜单排序、启停、展示模式，以及选中条目的详情面板。
- 应用启动、自定义命令、目标路径／当前目录执行模式。
- 组合命令及步骤排序、启停、校验。
- 新建空文件、文本内容模板、复制文件模板，以及模板资源变化提示。
- 拷贝路径、清理 node_modules。
- 扩展健康检查、发布同步状态、错误提示及部分自动修复、旧扩展维护。
- 首次设置向导、开机自启和应用更新。

README 的功能列表明显比实现简略，应同步更新，避免用户无法发现已有能力。

## 三个视角的 15 个想法

这些是候选方案，不代表全部应该实现；跨视角互补的想法在优先项中合并。

| 编号 | 视角 | 想法 | 最小范围与价值 |
|---|---|---|---|
| P1 | 产品 | 首次成功闭环 | 用户进入验证前发布所选应用，提供打开测试目录、成功确认和失败排查入口。 |
| P2 | 产品 | 配置备份与迁移 | 手动导入／导出菜单与模板配置；导入前展示差异、失效路径和冲突，降低换机重建成本。 |
| P3 | 产品 | 常用工作流预设 | 提供少量基于已安装应用的预设，例如同时打开编辑器和终端；先验证需求，再考虑模板库。 |
| P4 | 产品 | Finder 多选支持 | 先明确多选时的行为，优先支持复制多条路径，再按条目能力扩展批量打开。 |
| P5 | 产品 | 新建文件结果预览 | 展示将创建的文件名和内容，后续根据需求增加创建时命名或日期变量。 |
| D1 | 设计 | 统一编辑保存体验 | 清楚区分未保存、校验失败、已保存和同步中，支持放弃编辑；避免切换条目时意外保存或丢弃。 |
| D2 | 设计 | 真实目标的命令预览 | 选择实际文件／目录，展示工作目录、最终命令与目标含义；可显式发起试运行。 |
| D3 | 设计 | 错误直达配置 | 错误提示直接定位问题条目或步骤，并提供对应修复动作及结果。 |
| D4 | 设计 | 大菜单查找与批量管理 | 菜单项较多时按名称搜索、只看异常项、批量启停；排序操作保留清楚的全局位置语义。 |
| D5 | 设计 | 按上下文显示菜单 | 从仅文件／仅目录等简单条件起步，减少不适用的菜单项；需验证 Finder 上下文获取能力。 |
| E1 | 工程 | 组合命令失败策略 | 提供失败后停止／继续的明确语义和步骤结果，适配有依赖关系的工作流。 |
| E2 | 工程 | 执行结果闭环 | 在既有错误队列基础上关联条目与执行结果，先记录最近一次结果及时间，不急于建设完整日志平台。 |
| E3 | 工程 | 应用路径修复 | 应用移动后通过 bundle ID 查找候选位置，让用户修复失效引用；先核对现有发现机制能否复用。 |
| E4 | 工程 | 模板资源更新动作 | 在已有缺失／变化提示旁增加重新选择、重新同步和更新结果，避免用户仅看见警告。 |
| E5 | 工程 | 配置撤销与恢复 | 优先支持撤销删除、恢复上次有效配置；导入前保存快照，避免复杂配置重建。 |

## 优先推荐的 5 项

优先级综合考虑与可靠性目标的匹配、影响、实现成本及产品价值。未做竞品实测，“差异化”仅指潜在价值，不宣称竞品缺少这些能力。

| 顺序 | 优先项 | 目标匹配／预期影响 | 相对工作量 | 潜在产品价值 |
|---|---|---|---|---|
| 1 | 首次设置的真实验证闭环（P1） | 高；直接影响首次可用 | 小—中 | 强化首次成功与信任 |
| 2 | 编辑保存与有效状态一致（D1） | 高；贯穿日常配置 | 中 | 基础体验，降低配置不确定性 |
| 3 | 命令验证与错误恢复闭环（D2+D3+E2） | 高；影响所有自定义命令用户 | 中—大，可拆分 | 降低高级功能使用门槛 |
| 4 | 明确并完善多选行为（P4） | 高；覆盖 Finder 常见操作 | 提示小，批量执行中—大 | 符合用户对 Finder 操作的预期 |
| 5 | 组合命令失败策略（E1） | 对进阶用户高；总体覆盖待验证 | 中 | 支持有步骤依赖的工作流 |

### 1. 首次设置的真实验证闭环

**一句话方案：先应用配置并确认同步，再让用户进入 Finder 验证。**

- 依据：`RCMMApp/Views/Onboarding/OnboardingFlowView.swift` 中，进入 verify 步骤只切换页面，`applySelectedApps()` 在 `completeOnboarding()` 内才调用；`VerifyStepView.swift` 却已提示用户去右键并点击应用。
- 为什么入选：首次安装、尚无相关菜单时，所选应用尚未加入配置，验证操作与实际状态存在时序错位。这比继续增加菜单功能更应优先处理。
- 最小实现：进入验证前保存所选应用并等待发布结果；显示同步失败的原因；提供“打开测试目录”和“菜单未出现”的引导。重复返回步骤不能重复添加。保留跳过选项。
- 关键假设：目标用户会按向导顺序操作，并且首次运行没有可用的旧配置。
- 验证：用干净配置完整走一遍向导，在点击“完成”前验证所选应用已出现在 Finder 菜单。检查返回上一步、重复选择及编译失败分支。
- 成效指标：从首次启动到首次成功执行的时间、引导中验证成功比例；可先通过可用性观察收集，无需直接加入遥测。

### 2. 编辑保存与有效状态一致

**一句话方案：让用户明确知道编辑内容是否保存、是否有效、是否已在 Finder 生效。**

- 依据：`CommandEditor.swift` 有保存按钮，也在 `onDisappear` 保存；`CompositeCommandEditor.swift` 使用失焦／离开提交；`NewFileMenuEditor.swift` 的 `saveIfValid()` 会拒绝保存启用且有错误的模板草稿。
- 为什么入选：同类配置有不同提交规则，存在“以为没保存却已提交”或“改过但未生效”的理解风险；这属于需验证的体验判断，不等同于已复现数据丢失。
- 最小实现：先统一复杂编辑的草稿、保存／放弃和状态反馈；校验失败时明确保留草稿。即时启停和排序仍可直接生效，不必强行统一成提交表单。
- 关键假设：用户会在未完成编辑时切换菜单或设置页，且希望有明确的放弃编辑方式。
- 验证：让用户编辑命令、输入无效模板、切换条目，再询问哪份配置当前有效；检查实际持久化值与其预期是否一致。
- 成效指标：误判保存状态次数、无效草稿恢复成功率。

### 3. 命令验证与错误恢复闭环

**一句话方案：用真实目标预览命令，并从失败信息直接跳到可修复的位置。**

- 依据：`CommandEditor.swift` 的预览使用 `/Users/example/project`；`ErrorBannerView.swift` 展示最近 3 条错误，主要操作是打开设置或忽略全部；`ScriptExecutor.swift` 已有错误记录和成功日志，可作为完善基础。
- 为什么入选：系统已有校验、同步和错误基础设施，但用户仍需自行把“命令、目标、失败原因、配置位置”联系起来。
- 最小实现分两步：先支持选择真实目标预览、错误定位条目和最近结果；再增加用户明确触发的试运行。预览须复用实际命令替换与引用规则。
- 技术边界：主应用与 Finder 扩展执行环境不同，主应用试运行成功不能标记为 Finder 验证成功；应标明验证范围。脚本返回成功也不一定证明应用打开了期望目录。
- 关键假设：主要排障成本来自目标路径、命令内容或运行环境，而非单纯扩展启用问题。
- 验证：用含空格／中文路径、缺失应用及错误命令做任务观察，检查用户能否从错误定位并完成修复。
- 成效指标：从失败到修复的用时、重复出现的同类错误次数。

### 4. 明确并完善 Finder 多选行为

**一句话方案：多选时明确作用范围，并逐步让适合的菜单项处理全部选中对象。**

- 依据：`RCMMFinderExtension/FinderSync.swift` 的通用 `resolveTargetPath()` 对 `selectedItemURLs()` 返回 `selectedItems[0].path`；复制路径和通用脚本入口使用单个目标路径。部分条目还有专用目标策略，不能直接全部替换为循环执行。
- 为什么入选：用户可能以为操作作用于整个选择集，实际只处理首项。该行为可从源码确认，是否造成高频困惑需实际观察。
- 最小实现：先明确“不支持多选”的条目状态或作用范围；复制路径支持每行一条。随后分别定义应用启动、组合命令、新建文件在多选下的语义。
- 关键假设：批量选择足够常见，而且用户确实期望批量执行。
- 验证：覆盖两个文件、两个目录、混合选择、右键背景；检查界面表达与执行对象一致。验证前不要默认把含副作用的自定义命令对所有目标执行。
- 成效指标：目标遗漏次数、完成批量任务所需操作次数。

### 5. 组合命令失败策略

**一句话方案：明确每一步失败后是否继续，并展示失败步骤。**

- 依据：`RCMMApp/Services/ScriptSourceGenerator.swift` 的 `wrapComposite` 对步骤分别 try/catch，把错误收集到 `stepFailures`，结束时汇总报错；`CompositeMenuItemConfig.swift` 没有可配置的失败策略字段。
- 为什么入选：对于多个独立应用启动，继续执行合理；对于“准备文件→运行命令”这样的依赖链，用户可能希望前一步失败即停止。
- 最小实现：先在编辑器解释当前“失败后继续”行为；确认需求后提供组合级“失败后停止／继续”，旧配置保持原语义，并在结果中区分失败、成功和未执行。
- 关键假设：已有用户会创建有依赖关系的步骤，而不仅是同时打开多个应用。应用启动命令返回不代表应用已准备就绪，需避免承诺完整工作流编排。
- 验证：首步、中间步骤失败各做一次，确认停止／继续与预期一致，并验证旧配置兼容。
- 成效指标：失败后误执行步骤数、识别失败步骤所需时间。

## 后续候选与顺序调整条件

- **备份／迁移及撤销**：如果用户已维护大量自定义配置，或反馈过换机、误删问题，提升到前 3；当前没有用户证据支持优先做云同步。
- **模板资源修复与新建预览**：优先在现有缺失／变化提示上补动作；日期变量、创建时命名根据实际工作流再决定。
- **搜索、批量管理、上下文规则**：先观察用户菜单数量与查找困难；小菜单未必受益，条件规则还会增加“菜单为什么没出现”的解释成本。
- **安装体验**：README 明确当前发布包未做 Developer ID 签名和 notarization。若目标转向公开分发与新用户增长，应单独提升安装链路优先级；这是实际分发约束，不是一般性的风险提示。
- **README 更新**：作为低成本配套工作，补充已有功能及其入口。

建议先交付第 1 项的小范围修正，同时用 3—5 位目标用户完成首次设置、编辑命令和多选任务，验证第 2—5 项的相对优先级。当前未修改产品代码，也未运行构建或测试。
